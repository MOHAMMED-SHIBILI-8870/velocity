# Event-Driven Architecture

## Purpose

Velocity uses an event-driven architecture to decouple the matching engine from downstream business processes.

Instead of directly invoking services after executing a trade, the matching engine publishes domain events that are consumed asynchronously by independent subscribers.

This design keeps the matching path lightweight, deterministic, and extensible while allowing additional functionality to be introduced without modifying the matching engine.

---

# Why Event-Driven?

A successful trade triggers multiple independent operations:

* Update market data
* Update statistics
* Generate candlesticks
* Persist trades
* Perform settlement
* Notify users

Embedding all of this logic inside the matching engine would increase latency, introduce tight coupling, and make future development significantly more difficult.

Instead, the engine emits events and delegates downstream processing to subscribers.

---

# Architectural Overview

```text
                      Matching Engine
                             │
                             ▼
                     Domain Event Publisher
                             │
                             ▼
                     Event Dispatcher (Bus)
                             │
      ┌──────────────┬──────────────┬──────────────┬──────────────┬──────────────┐
      │              │              │              │              │
 Market Data     Statistics     Candles     Settlement    Persistence
      │
      ▼
 Public WebSocket
```

The matching engine is unaware of who consumes the events.

Subscribers can be added, removed, or modified without changing engine logic.

---

# Design Goals

The event system is designed to provide:

* Loose coupling
* High cohesion
* Extensibility
* Deterministic matching
* Asynchronous processing
* Independent subsystem evolution
* Simplified testing
* Improved maintainability

---

# Core Components

## Event Publisher

The publisher is responsible for emitting domain events generated by the matching engine.

The publisher knows:

* Event type
* Event payload

The publisher does **not** know:

* Who consumes the event
* How many subscribers exist
* What happens after publishing

---

## Event Dispatcher

The dispatcher acts as the internal event bus.

Responsibilities include:

* Registering subscribers
* Managing subscriptions
* Routing events
* Delivering events to interested consumers

The dispatcher is infrastructure and contains no business logic.

---

## Event Subscribers

Subscribers implement business behavior triggered by events.

Current subscribers include:

* Market Data
* Statistics
* Candle Generator
* Settlement
* Trade Persistence
* User Stream Publisher

Each subscriber is independent of the others.

---

# Current Domain Events

The primary domain event currently produced by the matching engine is:

## TradeExecuted

Published after a successful trade execution.

Typical payload includes:

* Symbol
* Buy Order ID
* Sell Order ID
* Trade Price
* Trade Quantity
* Timestamp
* Sequence Number

Additional event types may be introduced as the system evolves.

---

# Event Flow

A successful trade follows this sequence:

```text
Incoming Order
        │
        ▼
Matching Engine
        │
        ▼
Trade Executed
        │
        ▼
Publish TradeExecuted Event
        │
        ▼
Event Dispatcher
        │
        ├────────► Market Data
        ├────────► Statistics
        ├────────► Candles
        ├────────► Settlement
        ├────────► Persistence
        └────────► User Streams
```

The matching engine immediately returns to processing the next command without coordinating subscriber execution.

---

# Market Data Subscriber

The Market Data subscriber converts trade events into real-time exchange updates.

Responsibilities include:

* Updating ticker data
* Updating order book depth
* Publishing trade feeds
* Broadcasting market updates

These updates are distributed through the public WebSocket hub.

---

# Statistics Subscriber

The Statistics subscriber maintains rolling market statistics.

Current metrics include:

* Open Price
* High Price
* Low Price
* Last Price
* Base Volume
* Quote Volume
* Trade Count

These values are exposed through the Market Statistics service.

---

# Candle Subscriber

The Candle subsystem consumes trade events to generate OHLCV candlestick data.

Current responsibilities:

* Update Open
* Update High
* Update Low
* Update Close
* Update Volume

Future enhancements may include:

* Multiple candle intervals
* Historical aggregation
* Persistent candle storage

---

# Settlement Subscriber

The Settlement subsystem performs post-trade accounting.

Responsibilities include:

* Update wallet balances
* Consume locked funds
* Credit assets
* Update positions

Settlement is intentionally separated from matching to keep financial accounting independent.

---

# Persistence Subscriber

Persistence is handled asynchronously.

Responsibilities include:

* Store trades
* Store orders
* Store positions

The matching engine never waits for database writes.

---

# User Stream Subscriber

Private user notifications are generated from trading events.

Examples include:

* Order accepted
* Order partially filled
* Order fully filled
* Order cancelled
* Balance updated

These events are delivered through authenticated WebSocket connections.

---

# Decoupling Example

Without an event-driven architecture:

```text
Matching Engine
        │
        ├── Update Statistics
        ├── Update Candles
        ├── Persist Trade
        ├── Settlement
        ├── Broadcast WebSocket
        └── Notify Users
```

The engine becomes tightly coupled to every subsystem.

With an event-driven architecture:

```text
Matching Engine
        │
        ▼
Publish Event
```

Everything else reacts independently.

This significantly reduces complexity inside the engine.

---

# Event Ordering

Events are published only after successful command execution.

Execution order:

```text
Receive Command
        │
        ▼
Write WAL
        │
        ▼
Execute Matching
        │
        ▼
Generate Trade
        │
        ▼
Publish Event
        │
        ▼
Subscriber Processing
```

This guarantees that subscribers observe only committed state.

---

# Error Isolation

Subscriber failures should not compromise the matching engine.

If a subscriber encounters an error:

* The trade has already been executed.
* Engine state remains valid.
* Other subscribers continue processing.
* Recovery or retry mechanisms can be applied independently.

This prevents infrastructure failures from affecting trade execution.

---

# Advantages

The event-driven architecture provides several benefits:

* Loose coupling
* Independent subsystem evolution
* Improved maintainability
* Better scalability
* Easier testing
* Simplified feature additions
* Faster matching path
* Cleaner separation of responsibilities

---

# Future Evolution

The current in-process event dispatcher forms the foundation for future distributed messaging.

Potential future architecture:

```text
Matching Engine
        │
        ▼
Internal Publisher
        │
        ▼
Kafka / NATS
        │
        ├── Persistence Service
        ├── Analytics Service
        ├── Notification Service
        ├── Market Data Service
        ├── Risk Service
        └── External Consumers
```

Migrating to a distributed message broker should require minimal changes to the matching engine because event publication is already abstracted behind the publisher interface.
